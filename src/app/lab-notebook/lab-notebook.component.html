FIRST MEASUREMENTS · 28 SEP 2026

What does “fast”
actually feel like?

A tiny model can still make you wait. Loading weights, starting a worker, checking input, processing a prompt and producing the answer all contribute.

Our four measurements

Cold TTFTRequest sent to first non-empty output from a worker the server identifies as cold.
Warm TTFTThe same interval with a ready, warm worker.

These private Lambda tests include client/network time but exclude the website gateway and browser. They are small diagnostic samples, not medians, p95s or a latency guarantee. Cold workers were confirmed by worker IDs and AWS initialization records; image caching can vary.

Think’s first output is reasoning. Its answer began at 4.66 seconds warm. Flash generated 35/58 tokens, Think 158/159 and Goblin 64/64 (cold/warm), so total durations are not equal-length comparisons. Qwen used Q8_0; Goblin used the Edge checkpoint at step 61,177, with approximately 2B training targets.

We also hit real failures: an initial Flash load exceeded 45 seconds, an initial Goblin load hit Lambda’s 120-second timeout, and unrestricted Think used 512 tokens without an answer. We changed loading, bounded reasoning and retained the failures in the experiment record. More samples and quality evaluation come next.

Make comparisons fair

Pin model revision, hardware, runtime, quantization, prompt set, context lengths, output limits, sampling and concurrency. Keep Flash and Think results separate, record actual output length, and report median and p95 over repeated requests.

Cold starts must be confirmed by the serving system. A first browser request is not proof of a cold worker. Repeat cold measurements after a controlled worker restart, and record whether weights were already cached. Compare warmed workers separately.

Thinking can produce reasoning before the final answer. Record time to first reasoning output and time to first answer separately when evaluating perceived speed. Streaming packets are not tokenizer tokens.

What to try first

  1. Use a maintained serving runtime that supports the exact checkpoint and stream output as it arrives.
  2. Measure a warm-worker baseline, then the cost and latency tradeoff of scale-to-zero. Keeping a worker warm consumes resources.
  3. Compare quantization against the baseline on latency, memory and answer quality.
  4. Bound context and output lengths; measure prefix caching on repeated prefixes and concurrency on representative traffic.
  5. Keep the hardening check in the measured path. Speed improvements must preserve the checks and useful answer quality.

These are further experiments to run. The chat performance panel fills from actual completed responses and leaves unavailable measurements blank.

Both checkpoints scored 0/9 on six tiny function-completion tasks and three arithmetic tasks, using greedy CPU FP32 generation with a 64-token limit. This is a small authored diagnostic, not a general benchmark or a contamination audit. It does not establish that every prompt fails.

What this run can tell us

More training under the revised recipe improved held-out prediction. Data, optimizer arithmetic and the schedule changed together, so this is not an isolated test of one change. Useful coding, maths and coherent prose remain unproven.

The final weights were verified and the GPU stopped. A failed continuation with numerical collapse was abandoned before this healthy continuation; failures stay in the experiment history.

02 / THE ROADMAP

A small model.
A bigger learning question.

Each stage needs evidence before the next becomes a claim. This is a direction of travel, not a release-date promise.

  1. Current

    Make the base model measurable

    Train, save and evaluate reproducible checkpoints. Compare useful capability alongside loss, stability and compute cost.

    Next evidence: fixed evaluations, a validated 20B recipe, and a public run report.

  2. Next

    Open the chamber

    Contributions fill a real funding target. A verified ledger queues one bounded run when it is funded. Share its configuration, progress, failures and results in the notebook.

    Needed: payment account, deployed funding service and a tested hosted runner.

  3. Research

    Test learning that lasts

    Compare starting structures, sequential learning and retention. Test whether earlier experience makes a later task cheaper to learn.

    Evidence: new-task performance, old-task retention and matched compute budgets.

  4. Planned

    Give Goblin a useful interface

    Explore a small companion accessible through an API and MCP, usable alongside Codex and Claude. Keep input hardening at the boundary, with separate permissions and evaluations for tool use.

    Evidence: useful tasks, reliable serving, access controls and measured operating cost.

  5. Long term

    A personal Dave’s Brain

    A personal Goblin that can learn from experience while retaining useful knowledge. Supporter access is an idea to explore once serving costs and limits are understood.

    Open question: can the system improve how it learns, beyond simply receiving more training?

04 / THE RESEARCH QUESTIONS

What if experience made you a better learner?

The intuition starts with a newborn wildebeest: useful structure is already there. For Goblin, the question is which starting structures help a model learn, and how to measure that without assuming the answer.

Inductive bias / meta-learning

What should a learner start with?

Compare a useful initialization or architectural prior against an ordinary baseline, then measure adaptation on tasks excluded from training.

A useful test: equal compute and data, faster adaptation on genuinely held-out tasks.

Related work: Model-Agnostic Meta-Learning · Finn et al., 2017 ↗
Continual learning

Can it learn without losing what it knows?

Train on a sequence of tasks. Re-test earlier tasks after each update, rather than reporting only the newest capability.

A useful test: improved new-task performance with measured retention, compared with fine-tuning and replay baselines.

Related work: Overcoming catastrophic forgetting · Kirkpatrick et al., 2017 ↗
Learning to learn

Does experience improve the learning process?

Distinguish remembering an answer from learning a new task more efficiently. A learned update rule is one candidate; it also needs to generalize beyond its training tasks.

A useful test: fewer updates or lower compute to reach the same held-out performance, including the cost of learning the rule.

Related work: Learning to learn by gradient descent by gradient descent · Andrychowicz et al., 2016 ↗
Long-range question

Can it improve the mechanism that improves it?

Explore tightly scoped changes that can be tested and rejected. An agent modifying its code is a different claim from a base model becoming a broadly better learner.

A useful test: reproducible gains on untouched evaluations, with compute and human intervention accounted for. Goblin has not demonstrated recursive self-improvement.

Related work: Darwin Gödel Machine · Zhang et al., 2025 ↗
The ambition is an increasingly efficient general learner.

These are research questions. Training the current base model establishes a place to experiment; it does not yet establish the larger thesis.

05 / FILL THE TANK

One target.
One documented experiment.

The first proposed goal is US$72 for a 20B-token Goblin run. Contributions will fund compute, with the run and its findings recorded here.

Funding is not open yet.

There is no connected payment account or automatic GPU launcher. The tank is empty because no verified funding feed is connected. The $72 figure is an initial estimate, not a validated all-in quote.

How the tank will work

  1. Contribute through hosted checkout. Only verified payments count toward the tank; a browser click never changes the balance.
  2. When the target is reached, one launch job is queued for the agreed experiment. A full tank is not a claim that training has already started.
  3. The hosted runner starts the fixed recipe within its spend and time limits. The notebook records status, checkpoints, evaluations and failures.
  4. When training ends, compute stops. Results are shared whether or not the experiment improves the model.

Before contributions open

  • Connect a payment account and deploy the signed-event funding service.
  • Validate the 20B recipe and its compute estimate, including whether 20B means a fresh run or continuation to a cumulative target.
  • Set the hard compute budget and publish treatment of payment fees, excess contributions, failed runs and refunds.
  • Test the hosted launch, checkpoint backup and shutdown path. The existing local research controller is not sufficient for unattended public funding.

Will supporters get access?

That is the intention to explore: people who help fund Goblin could get an allowance to use it. Serving costs, availability and usage limits have not been set, so contributions are not yet being offered with an access entitlement.

Longer term, the goal is a Goblin companion that fits into tools such as Codex, Claude and MCP. The website has a signed-in Goblin preview; a supported external API and MCP adapter are future work.
