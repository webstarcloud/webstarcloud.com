THE MODEL LAYER · 30 SEP 2026

Two modes.
A base-model experiment.

The assistant uses Qwen3.5-0.8B, created by the Qwen team. Flash and Think change how that checkpoint is served. The menu also includes Goblin, my experiment in training a small base model from scratch.

Live · direct answers

Flash

Non-thinking generation, with a response limit of 128 tokens. A small token budget reduces work but can also truncate a useful explanation.

Default · bounded reasoning

Think

The same weights with thinking enabled, a 128-token reasoning budget and a 512-token total response limit. The extra budget does not add missing knowledge or guarantee a correct answer.

Search-backed requests use direct generation in both modes. In our diagnostic probes, the tiny model could loop or add unsupported details while reasoning over correct excerpts. The current retrieval prompt asks for a short answer supported by the supplied sources.

See what those probes found →

Why quantize?

Both modes use Q8_0 weights with llama.cpp in separate 4 GB ARM64 CPU Lambda workers. Q8_0 stores weights in blocks using 8-bit values with scaling information, reducing the weight footprint compared with 16-bit storage. Runtime buffers and context still need memory.

Quantization changes the representation of the weights; it does not train new knowledge into them. We have not established its answer-quality tradeoff with a controlled comparison against unquantized serving.

What “routing” means today

You choose the mode. Explicit rules then recognize simple arithmetic, owner-profile questions and factual lookups. A calculator or maintained profile can answer without loading the model. Search returns evidence for generation; an unavailable lookup returns an honest failure.

There is no learned model selector or squad of models collaborating on a request yet. Testing when a small model is enough requires a fixed task set, a stronger reference and a cost-aware routing policy.

FIRST MEASUREMENTS · 28 SEP 2026

What does “fast”
actually feel like?

A tiny model can still make you wait. Loading weights, starting a worker, checking input, processing a prompt and producing the answer all contribute.

Our four measurements
MetricWhat we measure
Cold TTFTRequest sent to first non-empty output from a worker the server identifies as cold.
Warm TTFTThe same interval with a ready, warm worker.
Tokens / secondNative engine decode rate, or output tokens after the first divided by server-measured first-to-last-token time.
Total response timeRequest sent to the final completed event, including protection, queueing and transport.

How the chat measures it

The browser starts its clock before acquiring the access token and sending the request. First output means the first non-empty answer or reasoning delta, not the first HTTP header or metadata event. First answer is recorded separately. Total time ends when the completed event is received, after recording and the cost-comparison receipt are finalized.

Cold and warm labels come from the server. The final receipt corrects the state to unknown when a tool answers without loading the model. Missing measurements stay unavailable. The interface keeps the completed response time and token count beside each answer; the detailed measurements belong in these research notes.

Decode rate comes from the engine’s timing and output token count, with a server-timed fallback when available. Network packets and rendered characters are not tokens. A calculator response bypasses generation and has no model decode rate.

The animated “Thinking…” text is a waiting state. Real tool events show calculator, source-lookup or maintained-profile activity. The waiting label stops at the first answer delta even when measured TTFT occurred earlier, during model reasoning.

What does the cost comparison count?

The chat shows a cumulative estimate across completed, priced model requests since tracking began. It compares native input and output token counts with an assumed frontier API rate of US$3 per million input tokens and US$15 per million output tokens, then subtracts measured model-worker compute at the 4 GB Ireland ARM Lambda list rate.

These are approximate reference rates, not the price of a named model. Different tokenizers, reasoning budgets and answer quality limit the comparison. The calculation excludes gateway and search execution, initialization and export overhead, storage, failed or stopped requests, and discounts. It is a model-compute difference, not the service’s net bill savings. Calculator/profile answers and missing usage remain unpriced; unavailable totals stay blank and a negative difference stays negative.

Make comparisons fair

Pin model revision, hardware, runtime, quantization, prompt set, context lengths, output limits, sampling and concurrency. Keep Flash and Think results separate, record actual output length, and report median and p95 over repeated requests.

Cold starts must be confirmed by the serving system. A first browser request is not proof of a cold worker. Repeat cold measurements after a controlled worker restart, and record whether weights were already cached. Compare warmed workers separately.

Thinking can produce reasoning before the final answer. Record time to first reasoning output and time to first answer separately when evaluating perceived speed. Streaming packets are not tokenizer tokens.

What to try first

  1. Use a maintained serving runtime that supports the exact checkpoint and stream output as it arrives.
  2. Measure a warm-worker baseline, then the cost and latency tradeoff of scale-to-zero. Keeping a worker warm consumes resources.
  3. Compare quantization against the baseline on latency, memory and answer quality.
  4. Bound context and output lengths; measure prefix caching on repeated prefixes and concurrency on representative traffic.
  5. Keep the hardening check in the measured path. Speed improvements must preserve the checks and useful answer quality.

These are further experiments to run. Completed-response metrics and diagnostic reports provide observations; neither establishes broad reliability.

INPUT PROTECTION · 30 SEP 2026

Before the model
sees your prompt.

Text can contain more than it appears to. The input check makes some of those differences visible before a question reaches a tool or model.

Implemented

A check at the boundary

The private worker runs llm-input-hardening with the strict_exec policy. It checks user messages and conversation context for hidden controls, misleading Unicode and encoded obfuscation. A blocked input does not proceed to generation. If the check is unavailable, the request stops.

The input inspector in the chat exercises this package separately. It sends text only when you press “Check input” and returns a decision and reason codes. It does not call the language model.

Try the full text inspector →

False positives are a system failure too

Earlier in development, ordinary questions such as “who is david webster” and “what is lotr?” were stopped. The current handling checks user input and prior assistant output separately; flagged assistant history can be dropped with a context notice instead of treating the next user message as the problem.

That tradeoff needs testing on real conversations. A permissive check can miss obfuscation; an overbroad check can prevent harmless use.

“Input checked” does not mean “safe instructions.”

Plain text can still attempt prompt injection. This check does not establish factual truth, grant tool permissions or make a retrieved page trustworthy. Access controls, bounded tools and source handling remain separate parts of the design.

What I want to measure next

Use a reviewed corpus of benign multilingual inputs, known obfuscation cases and ordinary multi-turn conversations. Report both false blocks and missed cases, alongside inspection latency. A green status alone is not an evaluation.

WEB SEARCH · 30 SEP 2026

Retrieval changes
the trust boundary.

Adding search gives a small model evidence it did not have. It also gives the system another source of mistakes and untrusted instructions.

Implemented

Selected pages first. Whole-web fallback second.

Explicit rules recognize factual questions. A small index checks exact selected pages from the Omarchy manual, Dutch Royal House, Qwen documentation and Python tutorial. It ranks excerpts by term overlap and requires a relevant subject match; it is not a semantic search engine.

Snapshots are refreshed manually and expire after seven days. If indexed evidence is missing, stale or insufficient, a private SearXNG Lambda queries Google, Bing and DuckDuckGo. Engines can be unavailable or block requests. Search snippets are not full-page verification.

What leaves the conversation?

Only the current question is passed to the search worker, not chat history, identity or access tokens. On a whole-web fallback, that question reaches the configured upstream search engines. A match in the index stays inside the AWS service.

Search is behind the signed-in gateway, shared quotas and a separate monthly lookup-attempt limit. The service has no paid search API subscription; AWS execution, storage and logs still cost money.

A source is data, not an instruction

The worker validates source URLs, strips markup and checks source text. Bounded excerpts enter a separate untrusted-data section of the prompt. Users cannot choose an arbitrary fetch URL or change the engine list through the chat.

Those measures reduce exposure; they do not prove a retrieved passage is safe or true. A poisoned result can still mislead the model. Tool permissions must never come from a page’s instructions.

From pasted snippets to generated answers

An earlier version displayed source excerpts directly. It avoided some invented details but often failed to answer the question. The current version streams a concise model-generated answer using those excerpts as context. Source cards are attached by the service, rather than trusting the model to invent links.

When no usable evidence is found, the system says it could not verify the answer. When evidence is found, generation can still be wrong. Our probes caught correct names paired with incorrect historical claims.

Read what the probes actually established →

The selected-page index is small and manually maintained. This note describes the current implementation, not a claim of complete web coverage.

EVALUATION · EARLY DIAGNOSTICS · 30 SEP 2026

“It feels smarter”
is a terrible metric.

An answer can contain the expected name and still be wrong. That happened in our own checks, which is why a passing keyword match is not a factual-accuracy score.

What the probes caught

A small diagnostic set covers the Dutch king, Willem van Oranje, Omarchy installation, a fictional product, decimal arithmetic and assistant identity. Local runs use fixed source excerpts, so they test answer behavior separately from live retrieval.

Some responses named the right person but invented dates or confused a lifespan with the period of a historical event. A leaf-count question produced contradictory, repetitive prose. Correct source text and a “be accurate” instruction were not enough.

What changed, and what we checked

The current system uses a bounded decimal calculator for simple arithmetic, a shorter retrieval prompt, direct generation for source-backed answers and a repetition cutoff. These changes target observed failures; the cutoff detects some loops, not factual errors.

Final private Lambda smoke checks on 30 September returned “King Willem-Alexander” and identified Omarchy as an Arch- and Hyprland-based Linux distribution. Decimal addition returned exactly 0.3 without a model call. These were a few diagnostic requests, not a representative benchmark or a signed-in browser test.

A local compound question about Willem van Oranje still lost part of the requested historical explanation. Shorter answers can remove hallucinations and useful content at the same time.

Software correctness and answer quality need different tests.

Unit and integration tests check parsing, authorization, streaming and error behavior. They cannot establish that the assistant consistently answers real questions correctly. Prompt probes reveal examples, not population-level accuracy.

Code inspection · 30 Sep 2026

When a valid citation is still a wrong review

I tried asking two small models to review eight synthetic Angular excerpts: four with authored bugs and four corresponding clean controls. The freeform outputs had to cite a real path, line and matching source text. Passing that check did not make the diagnosis correct.

Source/schema checks validate output structure and citations, including empty findings. The bug and false-alarm counts come from assistant inspection of these examples, not a human accuracy grade. The saved reports leave semantic scores ungraded. Different models and quantization, tiny samples and no repeated trials prevent a general capability comparison.

One coder response quoted takeUntilDestroyed while claiming the subscription had no cleanup. Angular documents that this operator completes the observable when its context is destroyed. The citation was valid; its interpretation was wrong.

Give the model a smaller job

The current inspection starts with fixed structural observations. A button without an explicit type inside a form prompts a check of intended submit behavior. An explicit HTML sanitization bypass prompts a check of where its input comes from. Neither alone proves a bug or an exploitable vulnerability. Partial excerpts cannot establish that lifecycle cleanup is absent elsewhere.

The model selects supplied observation IDs; fixed text and source links form the answer. Both guided variants passed all eight fixture checks, including cases needing no model call. That validates this narrow observation and selection contract, not general bug detection. I chose to reuse the existing Qwen worker rather than add a separate live coder worker.

Keep the experiment bounded

A request reads at most two files and 6,000 bytes of excerpts from an immutable revision of the public website repository. Selection allows at most two calls of 128 output tokens each, sharing one 75-second deadline; the second is only for an invalid selection. Unvalidated selection falls back to fixed observations. The response states that tests were not run. It cannot edit files or deploy changes.

Try asking “Review the website repository” in the chat. Treat the result as a guided inspection of a small sample, with explicit limits on what the model can conclude.

Next evaluation work

A useful score needs a useful test

  1. Keep a held-out prompt set separate from the examples used to tune prompts and routing.
  2. Check retrieval relevance before judging whether an answer is supported by its sources.
  3. Score correctness, completeness, appropriate uncertainty and task completion, with manual review of failures.
  4. Pin model, quantization, prompts and serving limits; repeat runs to expose variability.
  5. Report quality alongside latency and compute cost. A faster incomplete answer is a different result.

A broader evaluation suite is planned. Until it exists, these pages will keep the claim narrower than the ambition.

04 / THE RESEARCH QUESTIONS

What if experience made you a better learner?

The intuition starts with a newborn wildebeest: useful structure is already there. For our experiments, the question is which starting structures help a model learn, and how to measure that without assuming the answer.

Inductive bias / meta-learning

What should a learner start with?

Compare a useful initialization or architectural prior against an ordinary baseline, then measure adaptation on tasks excluded from training.

A useful test: equal compute and data, faster adaptation on genuinely held-out tasks.

Related work: Model-Agnostic Meta-Learning · Finn et al., 2017 ↗
Continual learning

Can it learn without losing what it knows?

Train on a sequence of tasks. Re-test earlier tasks after each update, rather than reporting only the newest capability.

A useful test: improved new-task performance with measured retention, compared with fine-tuning and replay baselines.

Related work: Overcoming catastrophic forgetting · Kirkpatrick et al., 2017 ↗
Learning to learn

Does experience improve the learning process?

Distinguish remembering an answer from learning a new task more efficiently. A learned update rule is one candidate; it also needs to generalize beyond its training tasks.

A useful test: fewer updates or lower compute to reach the same held-out performance, including the cost of learning the rule.

Related work: Learning to learn by gradient descent by gradient descent · Andrychowicz et al., 2016 ↗
Long-range question

Can it improve the mechanism that improves it?

Explore tightly scoped changes that can be tested and rejected. An agent modifying its code is a different claim from a base model becoming a broadly better learner.

A useful test: reproducible gains on untouched evaluations, with compute and human intervention accounted for. Our models have not demonstrated recursive self-improvement.

Related work: Darwin Gödel Machine · Zhang et al., 2025 ↗
The ambition is an increasingly efficient general learner.

These are research questions. Training the current base model establishes a place to experiment; it does not yet establish the larger thesis.

The About page shows the reported US$24.22 while payment setup is unconfigured. A future verified feed will replace this report rather than add it, so the same donation is never counted twice. Existing contributions need reconciliation before that feed is connected. The displayed balance does not queue a training job or authorize spending.

How online funding will work

  1. Contribute through hosted checkout. Only verified new payments enter the payment ledger; existing reported donations are reconciled separately. A browser click never changes the balance.
  2. When the target is reached, one launch job is queued for the agreed experiment. Reaching the target is not a claim that training has already started.
  3. The hosted runner starts the fixed recipe within its spend and time limits. The notebook records status, checkpoints, evaluations and failures.
  4. When training ends, compute stops. Results are shared whether or not the experiment improves the model.

Before online checkout opens

  • Connect a payment account and deploy the signed-event funding service.
  • Validate the 20B recipe and its compute estimate, including whether 20B means a fresh run or continuation to a cumulative target.
  • Set the hard compute budget and publish treatment of payment fees, excess contributions, failed runs and refunds.
  • Test the hosted launch, checkpoint backup and shutdown path. The existing local research controller is not sufficient for unattended public funding.

Will supporters get access?

That is the intention to explore: people who help fund the research could get an allowance to use it. Serving costs, availability and usage limits have not been set, so contributions are not yet being offered with an access entitlement.

Longer term, the goal is a personal assistant that fits into tools such as Codex, Claude and MCP. The website has a signed-in assistant preview; a supported external API and MCP adapter are future work.
